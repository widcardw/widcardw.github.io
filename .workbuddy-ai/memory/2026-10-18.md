## 主题切换动画：环形遮罩 → 整页淡变

用户反馈右上角主题按钮的环形遮罩（circle clip-path + View Transition）点击时会闪，希望改成整页直接切换或渐变。

改动：
- `src/components/dark/ThemeToggle.tsx`
  - 删除 `cycleTheme` 里的 `clipPath` / `endRadius` / `transition.ready` 环形动画逻辑
  - 新增常量 `THEME_TRANSITION: 'fade' | 'instant'`（默认 `'fade'`），一行可切回瞬切
  - 保留 `document.startViewTransition()`，加 `prefers-reduced-motion` 降级为瞬切
  - `realTheme` signal 与导出保留（Giscus 评论框主题依赖它）
- `src/components/dark/ThemeToggleButton.css`
  - 删掉旧的 `.dark::view-transition-*` z-index 翻转规则（环形动画专用）
  - `::view-transition-old(root)` 固定 `opacity:1; animation:none; z-index:1`（旧快照垫底不动）
  - `::view-transition-new(root)` 上层 `theme-fade-in 360ms cubic-bezier(0.4,0,0.2,1)`
  - 关键点：不做交叉淡变（old 也淡出），否则中途会透出背景，正是"闪"的来源

验证：用 playwright-core + 本地 chromium 实测亮度采样，亮 246 → 203 → 61 → 26.5 → 25.5，确认是连续渐变而非瞬切；100 页构建通过，零控制台错误。

备注：构建需 `env -u CODEBUDDY_SAFE_DELETE_BULK_STATE_DIR -u CODEBUDDY_TOOL_CALL_ID`，否则 Astro 清理 dist 会触发沙箱批量删除保护而卡住。

## 图片资源组织方式调研（未动手，等用户决定）

用户问是否该把图片从 `_public` 挪到文章同级目录。结论：应该，官方推荐，且能拿回图片优化。

现状机制：
- `publicDir: 'src/content/blog/_public'`，所以 `![[_public/updater/a.png]]` → resolver 去掉 `_public/` → `<img src="/updater/a.png">`
- 图片全是原样复制，**完全不经过 Astro 图片管线**；副作用是 alt 变成文件路径

实测验证（临时建 md + 相对路径图片，构建后检查产物，已清理）：
- `![](./assets/x.png)` 在自定义 `unified` processor 下**仍然走优化**：生成 `/_astro/x.hash.webp`，带 `loading="lazy"`、`decoding="async"`、`width/height`
- 2.1K png → 926B webp
- 结论：`markdown.processor` 换成 unified 不影响图片优化，两者是独立链路

改动量（脚本统计）：
- 13 篇文章含图片，54 个不同资源，57 条引用
- 跨文章共用只有 2 个：`updater/InterpolateExampleScene.png`（c01/c04）、`gl/quadratic-bezier-stroke-shader.excalidraw.svg`（两篇 GL）
- 目录现状：updater 19（6 篇共用）、posts-imgs 22（4 篇共用）、learn-git 9（1 篇）、avatar 11（全站共用）、gl 5、md-plugins 3

三个技术限制（迁移时必须处理）：
1. mp4 视频 11 个：Astro 图片管线不处理视频，`![](x.mp4)` 会渲染成 `<img>` 坏掉，必须留 public 或写 `<video>`
2. gif 3 个：动态 gif 经 sharp 转 webp 有丢动画风险，建议留 public
3. MDX 的相对路径图片行为尚未实测（md 已确认可行）

Obsidian 侧兼容：`![[x.png]]` 是按文件名全局解析、不依赖路径；`![](./assets/x.png)` 标准相对路径 Obsidian 也支持，配合设置「附件默认保存到当前文件所在文件夹的子文件夹」即可。

## 图片迁移已执行（方案 C：保留 wikilink 写法 + 走 Astro 图片管线）

### 关键发现
`@astrojs/markdown-remark` 的 `index.js` 里，`remarkCollectImages` 排在所有用户插件**之后**，源码注释：
`// Apply later in case user plugins resolve relative image paths`
→ 官方预留了「插件自行解析图片路径」的扩展点，方案 C 不是 hack。

链路：remark 插件生成标准 `image` 节点 → `remarkCollectImages` 收集 url → `rehypeImages` 检查 hast `<img>` 的 src 是否在 `localImagePaths` → 替换成 `__ASTRO_IMAGE_` → astro:assets 优化。

### 新增插件 `src/plugins/wiki/remarkWikiImage.ts`
- 构建期扫描 `src/content/blog` 建索引：`byName`（文件名→绝对路径）、`byRel`
- 解析顺序模仿 Obsidian：显式相对路径 → 相对当前 md → 相对内容根 → 按文件名全局查找
- 命中则替换成 `{ type: 'image', url: './xxx', alt, position }`，未命中保持原 wikilink（向后兼容）
- `IMAGE_EXT` 含 png/jpg/jpeg/webp/avif/svg，**不含 gif**（实测动图 gif→webp 体积从 181K 涨到 468K，虽保留 88/89 帧但不划算）
- 在 astro.config 的 remarkPlugins 里排在 `remarkWikiLink` 之后

### 迁移结果
- 移动 72 个文件：`_public/` 拆解为 `public/`（avatar、ads.txt、favicon、noface.gif）+ `public/media/`（11 mp4 + 3 gif + `_archive/` 6 个孤儿）
- 图片进 `posts/<分类>/assets/`：blog 9、manim 21、notes 6、write-plugins 3
- 57 条引用改写：图片 → `![[文件名]]`（短名，零冲突），视频 → `![[media/updater/x.mp4]]`
- `publicDir: 'src/content/blog/_public'` 已删除，回归默认 `public/`

### 踩到的坑
`image-size`（Astro 用）的 svg 检测只扫**前 1KB** 找 `<svg ...>` 标签。两个 drawio 导出的 svg（`example_trianglify.svg`、`updater_01interpolate.svg`）带巨大的 `content` 属性（内嵌 mxGraphModel），标签长度 6.5K/9.3K，导致 `NoImageMetadata` 构建失败。已删除 `content` 属性（仅 drawio 二次编辑用，渲染无关），原文件备份在 `/tmp/svg-backup/`。

### 验证
- 构建 100 页通过，165 个资源引用零死链
- 插件产出与迁移前完全一致：KaTeX 49、mermaid 8、callout 324、expressive-code 269、code-icon 102、mark 114
- 浏览器实测 24/24 图片加载成功（注意 headless 下 lazy 加载需强制 eager 才测准）
- 图片产出：`_astro/x.hash.webp` + `loading="lazy"` + `decoding="async"` + width/height

### Sätteri 调研（用户顺带问）
Astro 7 默认处理器，Rust 实现，插件体系是 `mdastPlugins`/`hastPlugins`（非 remark/rehype）。社区插件：`satteri-callouts`、`satteri-external-links`、`@jemjam/satteri-highlights`、`@nullpinter/satteri-katex`、`satteri-imgattr`。没有 wikilink/mermaid/code-icon/gl-preview/asciimath 的现成替代。官方文档明确：依赖 remark/rehype 生态的项目应继续用 Unified。结论：本项目不适合迁 Sätteri。
